## Findings requiring changes

### R1 — blocker / Critical: fresh ACL check retains stale superadmin organization authority

Location: `apps/mercato/src/modules/logistics/commands/context.ts:20–24`.

`resolveFresh` is not sufficient to make the returned organization scope independent of the incoming auth snapshot. `packages/core/src/modules/directory/services/organizationScopeService.ts:53–70` reloads ACLs but passes the original `auth` into `resolveOrganizationScope`. That resolver, at `packages/core/src/modules/directory/utils/organizationScope.ts:272–285`, uses `acl.isSuperAdmin || auth.isSuperAdmin`, making `allowedIds` null when the incoming flag is still true. Logistics then treats null as unrestricted even though its fresh ACL says the actor is no longer superadmin.

Concrete counterexample executed against the actual context helper, actual default scope service/resolver and actual feature-policy/wildcard code: tenant T contains A and B; fresh ACL is `{ isSuperAdmin: false, features: ['logistics.*'], organizations: [A] }`; context has `auth.orgId=A`, `auth.isSuperAdmin=true`, selected B. Authorization **succeeds for B**. Clearing only the incoming superadmin flag makes the identical call reject with 403. A user-level ACL can have exactly those independent feature/organization fields (`auth/services/rbacService.ts`, per-user ACL branch). Both acceptance and receipt reads use this helper, so an old context can mutate or replay scoped results after organization authority is revoked.

The normal interactive HTTP resolver refreshes the superadmin flag in `auth/lib/sessionIntegrity.ts:140–150`; this narrows the ordinary HTTP exposure to revocation between context construction and command authorization. It does not repair the command boundary's promised fresh authorization, including reused trusted command contexts. This is not a claim that an arbitrary forged JWT passes HTTP authentication.

Minimal fix: derive organization authority using the freshly loaded ACL's superadmin flag, never the previous context flag. Re-resolve/check selected-organization membership with that fresh authority, preserving legitimate current superadmin tenant overrides and descendant grants. Reject revoked override scope. Add a test through the real default scope resolver for the counterexample, its control, and replay; mocking `resolveFresh` with an already-safe scope cannot detect this.

### R2 — major / High: explicit null organization becomes an implicit write target

Location: `apps/mercato/src/modules/logistics/commands/context.ts:15`.

The contract requires an authenticated active organization and a scope-required error for null selection. Nullish coalescing instead invokes `resolveActiveOrganizationId`, whose documented purpose is to fall back to the actor's organization for configuration modules. With a superadmin viewing all organizations in their own tenant, `selectedOrganizationId=null`, `auth.orgId=null`, `auth.actorOrgId=A`, `auth.actorTenantId=auth.tenantId=T`, the logistics helper selects A and accepts a valid command for an A record. It should require explicit selection. This also silently scopes receipt lookup to A.

Executed source probe: real context helper plus real shared fallback function, a fresh-scope service stub accepting the supplied selected ID, and an authorized feature-policy stub returned A rather than 400. This proves the fallback branch, not an HTTP session test. The existing unresolved-organization unit case omits `actorOrgId`, so it misses this path.

Minimal fix: distinguish absent scope information from an explicit null/all-organizations selection. Require the trusted active selected organization for logistics; do not use the configuration-oriented actor fallback for an explicit null selection. Cover same-tenant all-organizations and foreign-tenant overrides, while preserving valid explicitly selected organizations.

## Other reviewed behavior

- **API keys:** platform subjects are `api_key:<uuid>` (`shared/lib/auth/server.ts:312`), and the real RBAC loader supports this prefix. The UUID check at `commands/context.ts:18` rejects every native key before fresh authorization; the probe confirmed 403. This is fail-closed, not a permission bypass. The accepted receipt model explicitly specifies `actorUserId: UUID` and the App Spec targets internal users, so API-key support is not invented as a release requirement here. If keyed invocation is intended later, specify principal identity and receipt namespacing before changing this; do not simply substitute a key UUID or trust a linked user without checking key grants.
- **Feature overrides:** the actual `authorizeFeatures` checks scope, removed features and disabled modules before unrestricted/wildcard allowance. Current explicit grants and `logistics.view` are required; additive ACL declarations leave default admin grants read-only as specified.
- **Versions:** strict UTC input and finite stored dates precede `assertOptimisticLock(..., envValue: 'all')`; global compatibility opt-out cannot disable the domain check. All three mutable entities use monotonic `max(now, previous+1ms)` hooks. Installed MikroORM `ChangeSetComputer.js:55–76` applies update initializers only after detecting a changed payload. Receipt results are collected after the first flush, including the hook's final version. The manual bump followed by a hook bump remains monotonic; the contract requires at least one millisecond, not exactly one.
- **Locks and atomicity:** the helper rejects `ctx.transactionalEm` and an already-transactional root EM, forks, then uses the real `withAtomicFlush` begin/phase-flush/commit path. The parameterized advisory lock receives `em.getTransactionContext()`. Receipt key includes tenant, organization, actor, action and request ID. Record locks are scoped, refreshed, pessimistic-write, deduplicated and sorted; kind order is driver, vehicle, job. Acceptance uses only one job anchor. No unsupported claim about future trip locks or absent-booking races is made.
- **Replay/results:** changed validated input conflicts before mutation; replay reauthorizes first (subject to R1/R2), loads normalized scoped result rows in sequence and returns original recorded versions without rereading current job state or repeating domain effects. The receipt unique key and result sequence uniqueness match the entity declarations. Two phases keep job write and receipt/results in the same outer transaction; precommit failure rolls them back together.
- **Encryption/schema:** the declared maps cover job customer/cargo/place/note snapshots and profile PII, with a registration hash sibling. Locked reads use scoped decryption. Actual platform subscriber hooks encrypt before create/update and decrypt afterward while protecting pending changes. Receipt results contain IDs, versions and revisions rather than PII. Both migrations and snapshot were inspected; 5 tables, 73 column types and every non-primary index name matched after normalizing PostgreSQL's default timestamp precision. UUID actor storage explains the API-key restriction. No schema was applied and no encryption round trip was executed.
- **Postcommit effects/index/cache:** acceptance queues the `logistics:transport_job` indexer and flushes it only after the helper commits, then emits the declared minimal accepted event. The real data engine emits `query_index.upsert_one`; the command bus separately derives cache targets from `buildLog.resourceKind` and the command ID. Absence of explicit cache aliases alone is not evidence of missed job invalidation. A propagated after-commit exception is reported and the committed receipt remains successful. However, default data-engine/event behavior can swallow indexing failures before the module catch; the mocked `flushOrmEntityChanges` rejection test does **not** prove telemetry for every real subscriber/index failure or projection recovery. Replay deliberately does not retry effects. Treat that as a platform behavior/integration limitation, not evidence of rollback or durable delivery.
